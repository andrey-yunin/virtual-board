# Виртуальная CAN-плата температурного контроля

**Тема выпускного проекта:** разработка драйвера символьного устройства, эмулирующего CAN-плату температурного контроля, с персональными буферами событий для каждого процесса.

**Уровень сложности: Medium.**

## Задача и назначение

При разработке программного обеспечения для электронных плат необходимо проверять его поведение при нормальной температуре, перегреве и охлаждении ниже допустимого предела. Воспроизведение таких условий на физическом оборудовании требует отдельного стенда и времени на подготовку испытаний.

Проект предлагает программную замену платы для таких проверок. Модуль ядра Linux хранит заданную пользователем температуру, контролирует её допустимые пределы и передаёт состояние платы через виртуальную CAN-шину. Разработчик может воспроизвести нормальную работу и температурные аварии командами терминала на обычном Linux ПК.

**Цель проекта — создать воспроизводимый источник CAN-сообщений о состоянии платы для проверки управляющего ПО без физического оборудования.** Температура задаётся пользователем и представляет собой эмулируемое показание датчика.

## Как работает устройство

После загрузки модуль предоставляет символьное устройство `/dev/virtual_board`. Пользователь задаёт температуру и допустимые пределы, затем запускает передачу. Модуль формирует CAN-кадры и отправляет их через подсистему SocketCAN в виртуальный интерфейс `vcan0`. Сообщения доступны принимающей программе или консольной утилите `candump`.

```text
Команды пользователя в терминале
               │
       /dev/virtual_board
               │
       Модуль виртуальной платы
       ├── Хранение температуры и пределов
       ├── Контроль состояния
       ├── Персональные очереди событий → read → программы-читатели
       └── Формирование CAN-кадров → vcan0 → принимающая программа
```

| Возможность | Поведение устройства |
| --- | --- |
| Задание температуры | Пользователь изменяет эмулируемое показание датчика |
| Настройка пределов | В модуле хранятся нижняя и верхняя допустимые температуры |
| Температурный контроль | Модуль автоматически определяет норму, низкую температуру или перегрев |
| Периодическая передача | В CAN-шину поступают температура и состояние платы |
| Аварийное уведомление | При смене температурного состояния отправляется отдельное сообщение |
| Восстановление | При возвращении температуры в диапазон авария снимается автоматически |
| Запуск и остановка | Пользователь включает и выключает CAN-передачу |

Рабочее состояние `state` принимает значения `stopped` и `running`. Независимое поле `temp_status` показывает результат температурного контроля: `normal`, `undertemp` или `overheat`. Температурная авария не останавливает передачу: принимающая программа продолжает получать актуальное состояние платы.

## Персональные буферы — основа уровня Medium

Каждый процесс, работающий с символьным устройством, имеет собственный буфер событий. События возникновения и снятия температурной аварии, запуска и остановки помещаются в персональные очереди подключённых читателей и извлекаются через `read` в порядке поступления.

Например, два процесса одновременно наблюдают за платой. При перегреве оба получают уведомление. Чтение события первым процессом не удаляет его из буфера второго.

| Свойство | Практический результат |
| --- | --- |
| Общие параметры платы | Все процессы наблюдают одно устройство с одной температурой и едиными пределами |
| Независимые буферы | Каждый читатель получает собственную последовательность событий |
| Ограниченная ёмкость очередей | Расход памяти контролируется |
| Учёт переполнения | Потери медленного читателя учитываются отдельно и не блокируют остальных |
| Синхронизация доступа | Одновременное управление и чтение не нарушают целостность данных |

Персональные очереди обслуживают пользовательское чтение. Передача CAN-кадров выполняется независимо от наличия читателей символьного устройства.

## Интерфейсы и требования к реализации

| Требование | Реализация в проекте |
| --- | --- |
| Символьное устройство | Узел `/dev/virtual_board` для работы пользовательских программ |
| `write` | Команды задания температуры, пределов, запуска и остановки |
| `read` | Получение событий из персонального буфера процесса |
| `ioctl` | Настройка параметров и получение состояния через консольную утилиту на C |
| `/proc` | Сводка параметров и состояний платы, сведения о потерях событий |
| `/sys` | Отдельные атрибуты температуры, пределов, рабочего и температурного состояний |
| Управление памятью | Выделение персональных буферов, проверка ошибок и корректное освобождение ресурсов |
| Сборка и загрузка | Makefile с целями сборки, загрузки и выгрузки модуля |
| Среда курса | Образ и ядро из репозитория курса, сборка и оптимизация ядра согласно первому ДЗ; файл `.config` в репозитории проекта |
| Документация | README с инструкциями сборки, загрузки, примерами `read`, `write`, `ioctl` и описанием `/proc` и `/sys` |
| Форма сдачи | Отдельный публичный репозиторий с историей разработки за несколько дней и несколькими коммитами |

Драйвер проверяет входные параметры, обрабатывает ошибки выделения памяти и CAN-передачи, обеспечивает безопасное завершение отложенной работы и освобождение ресурсов. Архитектура использует очереди FIFO, периодическую и отложенную обработку, а также примитивы синхронизации ядра.

## Демонстрация и проверка результата

Основной сценарий выполняется на Linux ПК с виртуальной CAN-шиной, без адаптера и физической платы. Управление производится командами терминала; CAN-кадры наблюдаются через `candump`, события — чтением символьного устройства, параметры и состояния — через `/proc` и `/sys`.

| Действие | Ожидаемый результат |
| --- | --- |
| Задать пределы 10–70 °C, температуру 25 °C и запустить передачу | Периодические CAN-сообщения с нормальным температурным состоянием |
| Изменить температуру на 85 °C | Состояние `overheat`, CAN-уведомление и событие в каждой очереди читателей |
| Вернуть температуру к 50 °C | Состояние `normal` и уведомление о снятии аварии |
| Установить 5 °C | Состояние `undertemp` и уведомление о низкой температуре |
| Проверить значения ровно на границах 10 и 70 °C | Состояние `normal` |
| Запустить два независимых читателя | Оба получают события без взаимного удаления данных |
| Изменить параметры через C-утилиту | Подтверждение работы `ioctl` и обновления состояния |
| Передать некорректные параметры | Ошибка операции без повреждения действующих настроек |
| Остановить передачу | Состояние `stopped`, прекращение отправки CAN-кадров |
| Закрыть устройство и выгрузить модуль | Освобождение ресурсов и удаление интерфейсов устройства |

Результат проекта — модуль ядра, консольная утилита для `ioctl`, проверки и документация, позволяющие воспроизвести работу виртуальной платы и продемонстрировать все обязательные возможности символьного устройства уровня Medium.
