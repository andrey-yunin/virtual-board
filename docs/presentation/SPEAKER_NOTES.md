# Заметки к выступлению

Версия 18.09.2026. Сопровождают восемь слайдов рабочей презентации. Регламент защиты пока неизвестен; длительность выступления уточним перед финальной редакцией.

## 1. Виртуальная CAN-плата

Проект эмулирует плату температурного контроля в ядре Linux. Пользователь задаёт показания датчика, а плата должна контролировать пределы и отправлять CAN-сообщения. Прикладная цель — воспроизводимые испытания управляющего ПО без физической платы. Учебная цель — выполнить требования Medium: символьное устройство с персональным буфером каждого процесса.

На текущем этапе проверен минимальный жизненный цикл модуля. Нельзя представлять температурную логику или отправку CAN как уже работающие.

## 2. Задача и границы

Температура задаётся, а не измеряется. Предусмотрены одна плата и один CAN-интерфейс. Пользователь управляет платой локально через write и ioctl. Приём управляющих команд по CAN не входит в проект. Графический интерфейс и физический адаптер не требуются.

Температура хранится целым числом в десятых долях градуса, без вычислений с плавающей точкой. Принятый диапазон — от −40 до +125 °C; начальная температура 25 °C, пределы 10–70 °C. Подробный контракт находится в PROTOCOL.md.

## 3. Кто за что отвечает

Сначала пользователь загружает драйвер vcan, создаёт интерфейс командой ip link add и включает его через ip link set. Наш модуль использует готовый интерфейс. Параметр can_iface сохраняет его имя, по умолчанию vcan0; допустимость строки уже проверяется при init; сам параметр не создаёт интерфейс и не открывает сокет.

В будущей реализации модуль создаст CAN-сокет ядра, привяжет его к выбранному интерфейсу и будет отправлять собственные кадры. Из терминала пользователь задаёт температуру, пределы и режим работы; candump принимает и показывает CAN-кадры.

Вопрос «Кто отправляет кадры — модуль или команда?» — в рабочем сценарии модуль. cansend применялся только для отдельной проверки шины. При выгрузке модуль освободит собственный сокет, но оставит созданный пользователем vcan0.

## 4. Персональные буферы

Состояние платы общее, но каждый процесс-читатель должен иметь собственную очередь событий. Модуль копирует событие в каждую очередь. Прочитанное процессом A событие остаётся доступным процессу B.

Согласованы 8 процессов и 64 события на очередь. При переполнении новое событие отбрасывается для соответствующего клиента и учитывается потеря. Правила владения при повторных открытиях, fork и dup ещё необходимо завершить до реализации; пока не заявляем, что каждый open равен отдельному процессу.

Для защиты потребуется фактическая демонстрация двух независимых читателей, затем переполнения у медленного читателя.

## 5. Два состояния и два пути

state определяет, включена ли CAN-передача. temp_status показывает положение температуры относительно пределов. Перегрев не останавливает плату. Возврат в диапазон автоматически снимает температурную аварию. Граничные значения входят в нормальный диапазон.

В running модуль должен отправлять статус периодически и уведомление при температурном переходе. В stopped CAN-передача прекращается, локальный температурный контроль сохраняется.

read устройства возвращает локальные события из FIFO; он не принимает CAN-кадры. Периодические статусы не заполняют FIFO. CAN-передача не зависит от наличия процессов, читающих символьное устройство.

## 6. Основа из курса

Используем уже разобранные механизмы: структуру модуля и таймер из ДЗ22, сокеты и последовательную workqueue из сетевого ДЗ14, FIFO из ДЗ11, списки и синхронизацию из ДЗ10/18, интерфейсы из лекций 31/33.

В выбранной архитектуре callback таймера назначает работу, а worker выполняет отправку. Персональные FIFO хранят данные для пользовательских процессов; workqueue хранит задания для выполнения ядром. Это разные очереди и разные потребители.

Сейчас это архитектурные решения. После реализации пояснения дополним конкретными функциями и проверками корректного завершения.

## 7. Подтверждённые результаты

17 сентября проверена шина: кадр 123#11223344, отправленный cansend, получен candump. Это тест среды, а не нашего CAN-протокола.

18 сентября пользователь собрал virtual_board.ko на ядре 6.8.0-38-generic, выполнил make load и make unload. Сообщения module loaded и module unloaded подтвердили вход в init и exit. Также добавлен и проверен строковый параметр can_iface: без аргумента чтение через sysfs вернуло vcan0, с аргументом загрузки can_iface=vcan1 — vcan1. Это проверка хранения строки, а не подключения к CAN. modinfo показал описание и тип параметра. После добавления vb_validate_params проверены оба пути: bad/name привёл к Invalid parameters, коду завершения insmod 1, сообщению ядра и отсутствию модуля в lsmod; затем загрузка с vcan0 прошла успешно, модуль появился в lsmod и был выгружен. Проверка вызывается в начале init и прекращается на первой ошибке; при отказе init exit автоматически не вызывается.

В минимальном модуле пока нет выделений памяти, таймеров и устройства, поэтому этот тест не доказывает корректность освобождения будущих ресурсов.

При сборке были сообщения о разных именах компилятора при одинаковой указанной версии и о пропуске BTF из-за отсутствия vmlinux. Сборка завершилась успешно.

Формальное соответствие требованию ядра курса пока не подтверждено, .config ещё не добавлен. В финальной версии указать фактическое решение, не скрывая этот пункт.

Числовые параметры также проверены: загрузка с температурой -400, пределами -400/1250 и периодом 10 завершилась успешно, sysfs вернул заданные числа; модуль затем выгружен. Пять отдельных неверных наборов проверили каждую ветвь отказа: температура 1251, нижний предел -401, верхний 1251, переставленные пределы 700/100 и период 9. insmod каждый раз вернул 1, журнал указал конкретное несоответствие, в lsmod модуль отсутствовал. Это проверки параметров загрузки, не работа температурной модели или таймера. Все граничные комбинации пока не перебраны.

Добавлен общий контекст board и резервирование одного номера символьного устройства. В проверке получен 511:0; запись 511 virtual_board появилась в /proc/devices и исчезла после выгрузки. Это подтвердило получение и парное освобождение первого ресурса. Затем зарегистрированы cdev, класс и устройство; узел /dev/virtual_board появился с правами 0600 root:root и номером 511:0, совпавшим с атрибутом dev в sysfs. После выгрузки узел и класс исчезли, запись номера удалена. Обработчики read/write/ioctl пока не реализованы; ошибки регистрации искусственно не вызывались. /proc/devices — штатный список ядра, не наш будущий файл состояния платы. Major динамический, число 511 не является константой проекта.

## Промежуточное состояние на конец 18.09

После испытаний устройства написаны инициализация рабочего состояния, разбор команд и применение temp/limits. Они ещё не собраны и не проверены через write. В контексте объявлены command_lock и wq, но сама очередь не создана. Эти изменения не добавляем к подтверждённым результатам слайда 7. Следующая демонстрация должна подтвердить полный путь write → workqueue → изменение состояния; затем — отправку CAN. Workqueue выполняет задания ядра, а будущие FIFO хранят события для процессов. Это разные механизмы.
