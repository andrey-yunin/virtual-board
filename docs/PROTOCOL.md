# Параметры платы и протокол

Дата: 17.09.2026. Пользователь принял предложенные параметры платы и CAN-протокол. Ниже также зафиксирован контракт read/ioctl для реализации. Обновление 22.09: write/read/ioctl реализованы и собраны; 22.09 подтверждены базовые read/ioctl и два читателя; граничные сценарии ещё не проверены. Распределение интерфейсов закреплено в INTERFACES.md.

## Параметры

| Параметр | Значение |
| --- | --- |
| Температура | От −40,0 до +125,0 °C, шаг 0,1 °C |
| Внутреннее представление | Знаковое целое в десятых долях °C: `253` означает 25,3 °C |
| Начальная температура | 25,0 °C (`250`) |
| Начальные пределы | 10,0–70,0 °C (`100`–`700`) |
| Допустимые пределы | В диапазоне температуры, нижний строго меньше верхнего |
| Начальное состояние | `stopped`, `normal` |
| Период CAN | По умолчанию 100 мс, допустимо 10–60 000 мс |
| Интерфейс | `vcan0`, имя задаётся параметром загрузки |
| Клиенты | До 8 процессов одновременно |
| FIFO | 64 события на процесс; при переполнении отбрасываем новое событие |

Вычисления выполняются целочисленно. Нормальный диапазон включает обе границы. При изменении температуры или пределов состояние пересчитывается. Изменение с `normal` на `overheat`, `undertemp` и обратно создаёт событие; изменение значения внутри того же состояния не создаёт температурного перехода.

## Текстовые команды write

Один вызов write содержит одну полную команду. Числа температуры в интерфейсе передаются в десятых долях градуса, без десятичной точки; это сохраняет простой разбор через kstrtoint из курса.

| Команда | Действие |
| --- | --- |
| `temp 253` | Установить 25,3 °C |
| `limits 100 700` | Установить пределы 10,0–70,0 °C одной операцией |
| `start` | Включить периодическую CAN-передачу |
| `stop` | Остановить CAN-передачу, сохранив локальный температурный контроль |

Допускается завершающий перевод строки от echo. Максимальная длина — 64 байта вместе с переводом строки; встроенный NUL, лишние аргументы и несколько команд отклоняются. Нулевой write возвращает 0 и ничего не меняет. Успешный write возвращает исходное число байтов. Неверные пределы не меняют ни одного поля.

Повторный start для работающей платы и stop для остановленной — успешные операции без повторных событий. При start первый периодический статус ожидается через установленный интервал. Период настраивается через ioctl; команды ioctl и формат read описаны ниже.

## CAN-кадры

Classical CAN, стандартные 11-битные ID, без RTR. Оба сообщения содержат 8 байт. Успешный тест `123#11223344` проверял только среду.

| CAN ID | Сообщение | Условие отправки |
| --- | --- | --- |
| `0x123` | Текущий статус | Периодически, только в running |
| `0x124` | Температурный переход | При изменении temp_status, только в running |

Общий формат позволяет расшифровывать оба сообщения одинаково:

| Байты | Поле | Кодирование |
| --- | --- | --- |
| 0–1 | Температура | Знаковое 16-битное целое, десятые доли °C, младший байт первым |
| 2–3 | Нижний предел | То же представление |
| 4–5 | Верхний предел | То же представление |
| 6 | temp_status | 0 = normal, 1 = undertemp, 2 = overheat |
| 7 | state | 0 = stopped, 1 = running |

Отрицательные значения — дополнительный код на 16 битах. Поля упаковываем явно; не отправляем C-структуру состояния платы целиком из-за padding и зависимости от layout. Служебная структура SocketCAN can_frame остаётся транспортным контейнером.

Примеры для работающей платы с пределами 10,0–70,0 °C:

| Ситуация | Представление candump/cansend |
| --- | --- |
| Периодический статус, 25,0 °C | `123#FA006400BC020001` |
| Переход к перегреву, 85,0 °C | `124#52036400BC020201` |
| Переход ниже диапазона, −5,0 °C | `124#CEFF6400BC020101` |

В stopped новые CAN-кадры не формируются, поэтому байт state у отправленных кадров равен 1. Состояние stopped наблюдается локально через read/ioctl/proc/sys. Остановка не отправляет отдельный финальный кадр.

## События read

Одна запись — строка ASCII с переводом строки. Порядок полей фиксирован:

```text
event=<type> temp=<value> low=<value> high=<value> state=<state> temp_status=<status> error=<errno>\n
```

В этой схеме `\n` обозначает один байт перевода строки. Значения `temp`, `low`, `high` — целые десятые доли °C, как в write и ioctl. Числа десятичные; перед положительным значением знак плюс не выводится.

| event | Когда возникает |
| --- | --- |
| `temp_transition` | Изменился temp_status из-за новой температуры или пределов |
| `started` | Успешный переход stopped → running |
| `stopped` | Успешный переход running → stopped |
| `can_error` | Ошибка CAN; условия и частоту публикации закрепим с политикой восстановления |

Пример строки после перегрева (завершается переводом строки):

```text
event=temp_transition temp=850 low=100 high=700 state=running temp_status=overheat error=0
```

Все поля — снимок в момент события. Для обычного события error=0, для can_error — отрицательный код ошибки Linux. Сообщение can_error не вводит отдельного состояния fault. Начальный снимок при open не создаём: текущее состояние запрашивается через GET_STATUS. Периодические CAN-кадры не создают локальных событий.

Один read возвращает не больше остатка одной строки. Если буфер короткий, остаток сохраняется для следующего чтения, новые события его не обгоняют. Нулевой read возвращает 0. Пустой read ждёт с возможностью прерывания сигналом, при O_NONBLOCK возвращает EAGAIN. Ошибка copy_to_user не уничтожает недоставленный остаток; если часть уже скопирована, возвращается её длина. Потоки одного процесса совместно потребляют одну очередь, независимые процессы — разные.

## ioctl и общий UAPI

Заголовок: [virtual_board_uapi.h](../include/virtual_board_uapi.h). Структуры одинаковы для модуля и C-утилиты, указатели и поля типа long отсутствуют. Все поля имеют ширину 32 бита. В ioctl используется порядок байтов хоста, в CAN — явно заданный little-endian формат.

| Команда | Определение | Аргумент | Право открытия |
| --- | --- | --- | --- |
| `VB_IOC_SET_LIMITS` | `_IOW('V', 1, struct vb_limits)` | Указатель на пару low_decic / high_decic, 8 байт | Запись |
| `VB_IOC_SET_PERIOD` | `_IOW('V', 2, struct vb_period)` | Указатель на period_ms, 4 байта | Запись |
| `VB_IOC_GET_STATUS` | `_IOR('V', 3, struct vb_status)` | Указатель на выходной снимок, 24 байта | Чтение |

GET_STATUS возвращает temperature_decic, low_decic, high_decic, period_ms, state, temp_status. Коды state и temp_status совпадают с кодами CAN. Все поля результата заполняются, структура предварительно обнуляется. Успех ioctl возвращает 0.

Изменяющие команды копируют аргумент до постановки работы. SET_LIMITS использует ту же операцию, что `write("limits ...")`. SET_PERIOD при running отменяет таймер и запускает новый интервал от момента применения; при stopped лишь сохраняет период. GET_STATUS возвращает согласованный снимок под mutex без изменения платы и без ожидания очереди событий.

| Ошибка | Результат |
| --- | --- |
| Неизвестная полная ioctl-команда, включая неверные размер/направление | ENOTTY |
| Недоступная пользовательская память | EFAULT |
| Значение температуры или периода вне допустимого диапазона | ERANGE |
| Нижний предел не меньше верхнего | EINVAL |
| Нет требуемого права чтения/записи у открытия | EBADF |

Ошибочный вход не меняет состояние. Отрицательные коды возвращает обработчик ядра; пользовательский ioctl возвращает -1 и устанавливает errno. Рабочая цель — x86_64 с нативной C-утилитой; поддержка 32-битных приложений потребует отдельного compat_ioctl и пока не заявляется.

Реализованный CLI boardctl: `status`, `limits <low_decic> <high_decic>`, `period <ms>`. Температура и start/stop пока управляются через write; дополнительных ioctl для них не требуется.

## Доступ после загрузки

Управление — через write/ioctl `/dev/virtual_board`. Числовые файлы `/sys/module/virtual_board/parameters/` имеют права 0444 и показывают текущие значения из board.status; начальные значения задаются аргументами insmod. Отдельные операции изменения одного предела через sysfs удалены; limits меняет пару целиком.

Контекст создаётся для любого открытия /dev; подписка на события действует при наличии читающего открытия. Повторные открытия и потоки одного процесса используют одну очередь. dup не увеличивает opens, поскольку разделяет struct file. Чтение унаследованного открытия другим процессом возвращает EXDEV; ребёнок должен открыть устройство заново. Release освобождает ссылку независимо от закрывающего процесса. Подробнее: INTERFACES.md.
