## 1. Виртуальная CAN-плата

**Путь / контекст:** Андрей Юнин • разработка ядра Linux • уровень Medium

Открыть выступление полным определением: я разработал драйвер символьного устройства, который эмулирует CAN-плату температурного контроля. Его прикладная цель — дать воспроизводимый источник сообщений для проверки управляющего ПО без физической платы. Температуру задаёт пользователь как показание виртуального датчика. Модуль определяет статус и передаёт его через виртуальный CAN-интерфейс. В демонстрации получателем выступает candump; отдельное управляющее приложение в проект не входит. Затем перейти к вопросу: какие ситуации нужно воспроизводить при такой проверке?

## 2. Зачем эмулировать температурную плату

**Путь / контекст:** Контекст проекта: проверка ПО электронных плат на обычном Linux ПК.

В согласованном описании исходная задача сформулирована через испытания программ для электронных плат. Нужно проверить поведение при норме, перегреве и температуре ниже предела, а затем при восстановлении. На физическом оборудовании это требует стенда и подготовки условий. Наш проект позволяет задавать показание датчика из терминала и наблюдать результат программно. Мы не моделируем тепловую инерцию, датчик, электрические свойства CAN или произвольный протокол реальной платы: формат сообщений определён проектом. Такой предел модели не мешает воспроизводить нужные логические переходы.

## 3. В основе — символьное устройство

**Путь / контекст:** Прикладная задача: CAN-плата • механизм Linux: драйвер символьного устройства

Сначала назвать механизм Linux: это драйвер символьного устройства, загружаемый как модуль ядра. Узел /dev/virtual_board — точка доступа приложений. Запись передаёт команды драйверу, чтение получает события, ioctl передаёт структурированные параметры и читает состояние. Температура и пределы существуют в памяти модуля, а не в содержимом обычного файла на диске. Термин «символьное» не означает, что интерфейс обязан быть только текстовым: ioctl у нас двоичный. Основу Medium составляет персональный FIFO процесса; чтение одним не удаляет копию события у другого. CAN — способ выдать состояние виртуальной платы принимающей программе. procfs и sysfs дополняют наблюдение. Далее показать конкретное действие пользователя и три видимых результата.

## 4. Одна команда — три видимых результата

**Путь / контекст:** write → board.status → локальное событие + CAN-уведомление

Начать с пользовательского смысла: температура выше верхнего предела. Команда вводится после start. В одной ветви видим новый снимок, во второй событие, в третьей CAN-кадр. Сокращённая строка события на слайде скрывает low/high/state/error. Полный пример строки события и таблица CAN-данных находятся в проверке 1 корневого README. CAN-пример вычислен из протокола. Не выдавать иллюстрацию за новую выполненную проверку.

## 5. Где находится виртуальная плата

**Путь / контекст:** tools/boardctl.c → src/ → SocketCAN / пользовательские чтения

Разделить userspace и kernel space. printf и boardctl инициируют write/ioctl; chardev принимает команду, worker выполняет, board изменяет состояние. Затем читатели видят снимки и события, а CAN-ветвь передаёт кадры через сокет. GET_STATUS читает состояние напрямую под mutex и не проходит через очередь команд. Схема упрощает внутренние вызовы, но сохраняет направления данных.

## 6. Файлы повторяют обязанности модуля

**Путь / контекст:** Kbuild объединяет src/*.o в virtual_board.ko; board.h связывает внутренние объекты

main.c определяет board и порядок init/exit; params.c валидирует параметры и предоставляет callbacks. chardev.c регистрирует cdev и реализует write/ioctl; open/read/release находятся в clients.c. worker.c связывает workqueue, completion и hrtimer. board.c реализует правила состояния. can.c инкапсулирует сокет и CAN-формат. proc.c и sysfs.c наблюдают состояние. boardctl.c — отдельная программа userspace. Kbuild перечисляет объекты модуля, UAPI используют обе стороны.

## 7. Makefile: собрать, загрузить, выгрузить

**Путь / контекст:** Makefile / Kbuild → virtual_board.ko; tools/boardctl.c → пользовательская утилита

Это прямое соответствие требованиям 3/5. make без аргументов выбирает all и собирает модуль и boardctl. Цель make делегирует сборку /lib/modules/$(uname -r)/build через KDIR и M=$(CURDIR); Kbuild перечисляет src/*.o для virtual_board.o. load зависит от make, поэтому собирает модуль перед insmod; отдельно утилиту эта цель не собирает. Перед загрузкой должен существовать vcan0, для передачи он должен быть UP. make load использует параметры по умолчанию: температура 250, пределы 100/700, период 100 мс, stopped. В инструкции README выбран явный insmod с периодом 1000 мс для удобства демонстрации. unload вызывает rmmod; все читатели /dev должны быть закрыты. Сборка подтверждена для 6.8.0-38-generic; здесь показаны реальные цели, а не сообщение о новом выполненном цикле загрузки. Фрагмент Makefile сокращён: пустые строки и остальные цели опущены.

Фрагмент `Makefile`; многоточие обозначает пропуск.

```makefile
all: make boardctl
load: make
	sudo insmod ./virtual_board.ko
unload:
	sudo rmmod virtual_board
make:
	$(MAKE) -C $(KDIR) M=$(CURDIR) modules
```

## 8. Три разных запроса к плате

**Путь / контекст:** chardev.c / clients.c / proc.c / sysfs.c ↔ tools/boardctl.c

Управление после загрузки идёт через /dev. Sysfs и procfs предназначены для чтения. Начальные параметры можно передать insmod. GET_STATUS не извлекает события. CAN передаёт периодический статус 0x123 и температурные переходы 0x124 при running.

## 9. Почему один cat ждёт, а другой отвечает

**Путь / контекст:** clients.c: vb_client_read • chardev.c: vb_ioctl • sysfs.c: state_show

Начальный снимок при открытии устройства не создаётся. Прошлые события новому клиенту не выдаются. Полный путь атрибута: /sys/class/virtual_board/virtual_board/state. Чтение разных sysfs-файлов — отдельные операции, а не единый атомарный снимок. GET_STATUS читает все поля под одним state_lock.

## 10. write: от команды к изменению платы

**Путь / контекст:** chardev.c → worker.c → board.c → clients.c / can.c

Проследить путь chardev.c → vb_submit_command → vb_command_work → vb_board_apply_command. Пользовательский указатель не передаётся worker: передаются данные ядра. При stopped температура меняется и локальное событие возникает, но CAN-уведомление не отправляется. Пределы включены в нормальный диапазон.

## 11. ioctl: управление и снимок состояния

**Путь / контекст:** tools/boardctl.c → chardev.c: vb_ioctl; include/virtual_board_uapi.h — общий контракт

Отдельно обозначить обязательную операцию ioctl. Пользовательская утилита на C открывает то же символьное устройство и передаёт код операции и адрес структуры. Общий UAPI использует поля фиксированного размера: SET_LIMITS — 8 байт, SET_PERIOD — 4, GET_STATUS — 24. Наш vb_ioctl проверяет полную команду, права открытия и копирование аргумента. Изменяющие операции преобразуются в board_command и выполняются общей очередью, как write. GET_STATUS копирует все поля под state_lock и выдаёт структуру через copy_to_user без worker. Неизвестная команда даёт ENOTTY, неверный доступ EBADF, недоступная память EFAULT. На слайде сокращённый фрагмент SET_PERIOD, не полная функция. Обычные команды подтверждены; отрицательные ioctl и изменение периода при running полностью не проверены.

Фрагмент `src/chardev.c`; многоточие обозначает пропуск.

```c
case VB_IOC_SET_PERIOD:
    // ... проверка права записи
    if (copy_from_user(&period, user_arg,
                       sizeof(period)))
        return -EFAULT;
    command.type = VB_CMD_SET_PERIOD;
    command.period_ms = period.period_ms;
    break;
// ... общий путь изменяющих команд:
return vb_submit_command(&command);
```

## 12. Температура и передача независимы

**Путь / контекст:** board.c: vb_calc_temp_status / vb_board_apply_command

Пример проверен 22 сентября через sysfs. Норма включает обе границы. Изменение пределов также пересчитывает диагноз. Запрещённая команда не должна частично изменять состояние: сначала проверяется новое значение. Числа представлены целыми десятыми долями градуса.

## 13. Как приложение находит наш драйвер

**Путь / контекст:** chardev.c: vb_chardev_init → board.devno / board.cdev / vb_fops

alloc_chrdev_region резервирует один номер major/minor и сохраняет его в board.devno. cdev_init связывает cdev с нашей таблицей vb_fops, а cdev_add регистрирует этот cdev для выделенного номера. class_create и device_create публикуют класс и объект устройства; в используемой системе devtmpfs/udev обеспечивают узел /dev/virtual_board. Имя пути удобно приложению, а связь с драйвером определяется типом символьного устройства и номером major/minor. При open ядро находит зарегистрированный cdev и его файловые операции; последующие read/write/ioctl попадают в обработчики через открытый файл. Это упрощённая схема маршрутизации без внутренних подробностей VFS. Память платы и FIFO не хранится в узле /dev. На следующем слайде показываем саму таблицу vb_fops.

## 14. Регистрация интерфейсов: /dev, /proc, /sys

**Путь / контекст:** chardev.c: vb_chardev_init • sysfs.c: vb_sysfs_init • proc.c: vb_proc_init

Задание требует регистрацию интерфейсов в /dev, /proc, /sys. Уточнить терминологию: мы создаём узел устройства и записи в существующих файловых системах, а не реализуем новую файловую систему. Для /dev cdev_add связывает выделенный номер с обработчиками; class_create и device_create публикуют объект, узел появляется через стандартные механизмы системы. Для /proc вызов proc_create("virtual_board",0444,NULL,&vb_proc_ops) регистрирует файл сводки. Для /sys класс и устройство задают каталог /sys/class/virtual_board/virtual_board/, а device_create_file добавляет атрибуты state и temp_status с show-callback. Числовые значения опубликованы отдельно как module_param_cb, права 0444. На выходе выполняются proc_remove, device_remove_file, device_destroy, class_destroy, cdev_del и освобождение номера. Обычный цикл создания/удаления интерфейсов подтверждён; искусственные отказы всех регистраций не испытаны. Для проверки появления после загрузки в README приведён ls -ld /dev/virtual_board /proc/virtual_board /sys/class/virtual_board/virtual_board. После unload отсутствие этих путей проверяется отдельно. Штатное создание и удаление уже наблюдалось; показанный слайд связывает этот результат с регистрацией.

## 15. read / write / ioctl: таблица обработчиков

**Путь / контекст:** chardev.c: vb_fops — адреса функций связывают операции с нашим кодом

Процесс вызывает read для открытого /dev/virtual_board. Ядро использует файловые операции устройства и вызывает vb_client_read из clients.c. cdev_init связывает объект cdev с таблицей vb_fops. Поля слева — контракт struct file_operations, функции справа — наш код. Регистрация не запускает чтение. Похожий приём далее повторяется с INIT_WORK и timer.function: ядро хранит адрес callback вместе с объектом. owner удерживает модуль при использовании устройства.

Фрагмент `src/chardev.c`; многоточие обозначает пропуск.

```c
static const struct file_operations vb_fops = {
    .owner = THIS_MODULE,
    .open = vb_client_open,
    .release = vb_client_release,
    .read = vb_client_read,
    .write = vb_write,
    .unlocked_ioctl = vb_ioctl,
};
```

## 16. Команда ждёт результата worker

**Путь / контекст:** worker.c: vb_submit_command и vb_command_work — фрагменты, пропуски отмечены

Команды и периодические работы находятся в общей ordered workqueue. Worker не берёт command_lock: его удерживает ожидающий отправитель. vb_submit_command нельзя вызывать из этой же очереди, иначе она будет ждать собственную работу. Completion сообщает окончание операции, mutex сериализует отправителей.

Фрагмент `src/worker.c`; многоточие обозначает пропуск.

```c
request->command = *command;
init_completion(&request->done);
INIT_WORK(&request->work, vb_command_work);
queue_work(board.wq, &request->work);
wait_for_completion(&request->done);
ret = request->result;
// ... vb_command_work:
request->result =
    vb_board_apply_command(&request->command);
complete(&request->done);
```

## 17. От start до периодического CAN-кадра

**Путь / контекст:** board.c: start → worker.c: callback / periodic_work → can.c: send_status

Callback не выполняет сетевую отправку и не захватывает mutex. tx_work — заранее созданный объект, переиспользуемый для отправок. Если работа уже ожидает в очереди, очередной тик не добавляет вторую ожидающую копию. Это не жёсткое реальное время; пропущенные периоды не воспроизводятся задним числом.

## 18. Четыре строки связывают таймер и worker

**Путь / контекст:** worker.c: vb_timer_callback — тело без комментариев

Не обещаем отдельного финального CAN-кадра stopped: протокол его не предусматривает. Проверены stop и повторный start, настройка периода при stopped. Перенастройка при running реализована, но отдельное runtime-испытание ещё не подтверждено. Отмена таймера ждёт выполняющийся callback. Четыре строки callback показаны в порядке выполнения. container_of получает board_ctx по вложенному tx_timer; queue_work ставит заранее созданную tx_work; hrtimer_forward_now переносит срок; HRTIMER_RESTART просит ядро снова поставить таймер. Отправка произойдёт в vb_periodic_work после возврата callback.

Фрагмент `src/worker.c`; многоточие обозначает пропуск.

```c
ctx = container_of(timer, struct board_ctx, tx_timer);
queue_work(ctx->wq, &ctx->tx_work);
hrtimer_forward_now(timer, ctx->tx_interval);
return HRTIMER_RESTART;
```

## 19. Как кадр добирается до candump

**Путь / контекст:** worker.c / board.c → can.c → SocketCAN → vcan0 → сокет candump

SocketCAN предоставляет семейство сокетов PF_CAN. Сокет модуля создан в ядре и привязан к ifindex vcan0. candump открывает собственный CAN_RAW-сокет в userspace. Путь доставки показан укрупнённо: отправка через сокет, обработка CAN-стеком и драйвером vcan, локальное получение кадра сокетом наблюдателя. vcan работает внутри одного Linux, без проводов и физического контроллера. Модуль не принимает команды из CAN. Локальные FIFO /dev не являются CAN receive queue.

## 20. Имя vcan0 превращается в привязку сокета

**Путь / контекст:** can.c: vb_can_get_ifindex / vb_can_init — фрагменты, проверки между ними опущены

До загрузки модуля пользователь выполняет modprobe vcan, ip link add dev vcan0 type vcan, ip link set dev vcan0 up. Это подготовка среды, не код virtual_board. В функции поиска проверяется dev != NULL и dev->type == ARPHRD_CAN; ifindex сохраняется до dev_put. sock_create_kern создаёт сокет и сохраняет адрес в board.can_sock. Пустой CAN_RAW_FILTER отключает приём, поскольку модуль не читает сокет. kernel_bind закрепляет выбранный индекс. При ошибках настройки sock_release освобождает сокет. На слайде выборочные строки, не полный безопасный шаблон init.

Фрагмент `src/can.c`; многоточие обозначает пропуск.

```c
dev = dev_get_by_name(&init_net, can_iface);
// ... проверка dev и ARPHRD_CAN
ret = dev->ifindex;
dev_put(dev);
// ... результат поиска -> addr.can_ifindex
addr.can_ifindex = ret;
ret = sock_create_kern(&init_net, PF_CAN,
    SOCK_RAW, CAN_RAW, &board.can_sock);
// ... проверка ret, пустой CAN_RAW_FILTER
ret = kernel_bind(board.can_sock,
    (struct sockaddr *)&addr, sizeof(addr));
```

## 21. 85 °C превращаются в байты CAN-кадра

**Путь / контекст:** can.c: vb_can_fill_frame — байты data[] и поля struct can_frame

Пакуем поля явно, не отправляем внутреннюю C-структуру целиком: у неё другой размер и возможен padding. vcan0 готовится вне модуля, модуль находит интерфейс и привязывает сокет. Успешная отправка означает принятие кадра сетевым стеком, а не подтверждение доставки физическому узлу.

## 22. Кадр передаётся сетевому стеку

**Путь / контекст:** can.c: vb_can_send_frame — фрагменты, пропуски отмечены

frame — локальный объект на стеке вызывающей функции; iov_base сохраняет его адрес, не копирует данные. vb_can_fill_frame заполняет frame перед kernel_sendmsg. Последний аргумент — размер всей struct can_frame, включая can_id и длину, не только data. Отправка идёт в контексте worker после снятия state_lock. ret сравнивается с sizeof(frame); полный результат преобразуется в 0, неполный в -EIO, отрицательный сохраняется. Успех означает принятие стеком, не доказательство физической доставки. MSG_DONTWAIT ограничивает ожидание сокетной операции, но не делает её допустимой для callback таймера.

Фрагмент `src/can.c`; многоточие обозначает пропуск.

```c
struct can_frame frame;
// ...
struct kvec iov = {
    .iov_base = &frame,
    .iov_len = sizeof(frame),
};
// ...
vb_can_fill_frame(&frame, can_id, status);
ret = kernel_sendmsg(board.can_sock,
    &msg, &iov, 1, sizeof(frame));
```

## 23. CAN down: плата продолжает попытки

**Путь / контекст:** can.c: vb_can_handle_result → clients.c: локальный CAN_ERROR

Оба типа отправки используют общий обработчик результата. Последний код ошибки принадлежит последовательному worker. В тесте по одному can_error на отключение. Журнал dmesg отдельно не подтверждался; задержка восстановления не измерена. Удаление интерфейса не равно down: автоматической перепривязки к пересозданному устройству нет.

## 24. Каждое ожидание решает свою задачу

**Путь / контекст:** board.h: command_lock / state_lock; board_client: fifo_lock / read_lock

Для публикации берутся state_lock, затем fifo_lock. Для чтения — read_lock, затем fifo_lock. Читатель отпускает read_lock перед ожиданием события. pending_events учитывает события в FIFO и событие с недочитанной строкой; атомарный счётчик не заменяет защиту самой очереди. Не заявлять отсутствие всех гонок: конкурентные испытания неполны.

## 25. Medium: персональный буфер процесса

**Путь / контекст:** board.c: событие → clients.c: vb_clients_publish_locked

Результат двух читателей подтверждён пользователем 22 сентября. Контекст привязан к TGID, поэтому потоки и повторные открытия одного процесса разделяют FIFO. Публикация идёт клиентам с читающим открытием. Максимум 8 клиентов. Переполнение отбрасывает новое событие и увеличивает lost_events; этот граничный сценарий пока не испытан. Это прямое соответствие требованию Medium. Контекст с FIFO создаётся при первом открытии данным процессом; для публикации клиент должен иметь читающее открытие. Разделение очередей обеспечивается отдельными board_client и kfifo, а не только разными файловыми дескрипторами. Два читателя подтверждают основной сценарий независимой доставки; расширенные проверки fork/dup и переполнения остаются отдельно.

## 26. read: события из персонального FIFO

**Путь / контекст:** clients.c: vb_client_read — фрагмент ветки пустого FIFO

Протокол частичного чтения реализован: один read отдаёт не больше остатка одной строки. Позиция увеличивается на реально доставленные байты, поэтому ошибка копирования не уничтожает остаток. Короткие чтения, сигналы, переполнение и O_NONBLOCK здесь описываются по коду, а не как завершённые испытания.

Фрагмент `src/clients.c`; многоточие обозначает пропуск.

```c
mutex_unlock(&client->read_lock);
if (file->f_flags & O_NONBLOCK)
    return -EAGAIN;
ret = wait_event_interruptible(
    client->read_wait,
    atomic_read(&client->pending_events) > 0);
if (ret)
    return ret;
```

## 27. Один процесс — один клиент и FIFO

**Путь / контекст:** clients.c: vb_client_open / vb_client_release; board.h: struct board_client

Не смешивать выделение памяти и сохранение адреса. private_data не содержит копию клиента. Последнее читающее закрытие очищает события, а последнее открытие освобождает клиент. Унаследованное другим процессом открытие нельзя читать: EXDEV, требуется новый open. Эти края контракта реализованы, но fork/dup отдельно не испытаны. На слайде opens означает число открытых файловых объектов, а не копий fd. Это уточнение важно для Medium: отдельный клиент создаётся по идентичности процесса, а повторный open возвращает связь с существующим клиентом. Поле file->private_data хранит его адрес. Все читатели имеют общий статус платы, но разные процессы не делят хранилище событий.

## 28. Одно состояние, разные формы чтения

**Путь / контекст:** chardev.c: GET_STATUS • sysfs.c / params.c: атрибуты • proc.c: снимок

Для proc используется собственный буфер снимка, не seq_file. Его mutex защищает совместное чтение одного открытого файла. Чтение proc не добавляет клиента устройства. В ioctl отсутствует compat_ioctl для 32-битных программ. Нулевой lost_events в демонстрации не доказывает корректность счётчика при переполнении.

## 29. Ошибка ресурса: проверить и откатить

**Путь / контекст:** clients.c: vb_client_alloc — фрагмент; аналогичные проверки есть в init подсистем

kzalloc возвращает NULL при отказе; проверяем client до разыменования. kfifo_alloc возвращает код ошибки: если не удалось выделить хранилище очереди, ранее выделенный контекст освобождается kfree. Наша vb_client_alloc передаёт ошибку как ERR_PTR; её вызывающий проверяет IS_ERR. Важно не путать соглашения разных API: class_create и device_create возвращают ERR_PTR, для них используются IS_ERR и PTR_ERR, а не только NULL. proc_create и alloc_ordered_workqueue проверяются на NULL. Для module init предусмотрены метки отката: например, при отказе proc уже созданные chardev/sysfs удаляются, затем отменяется таймер и завершается очередь, затем освобождается сокет. При неуспешном init обычный module_exit не заменяет этот откат. Эти ветки есть в текущем коде; искусственные отказы выделения памяти и всех регистраций не проверены.

Фрагмент `src/clients.c`; многоточие обозначает пропуск.

```c
client = kzalloc(sizeof(*client), GFP_KERNEL);
if (!client)
    return ERR_PTR(-ENOMEM);
ret = kfifo_alloc(&client->fifo,
    VB_EVENT_FIFO_CAPACITY, GFP_KERNEL);
if (ret) {
    kfree(client);
    return ERR_PTR(ret);
}
```

## 30. exit: освобождение ресурсов по зависимостям

**Путь / контекст:** main.c: vb_exit — тело без журнала; далее module_exit(vb_exit)

cdev/file_operations owner удерживает модуль при открытом устройстве. vb_params_set_ready(false) завершает доступ callback параметров. proc_remove завершает обращения proc. При ошибках init каждая ветка освобождает только успешно созданное. Обычное удаление proc/dev/sys подтверждено; принудительные поздние отказы регистрации не испытаны. В vb_chardev_exit также вызываются device_destroy, class_destroy и unregister_chrdev_region. Важно: персональные FIFO не освобождаются перебором из vb_exit; открытые файловые операции удерживают модуль через owner, клиенты освобождаются при последних release до штатной выгрузки. Числовые параметры отключаются через vb_params_set_ready(false) с синхронизацией callback. При неуспешном init используется отдельная цепочка goto-отката. Фрагмент показывает реальные вызовы vb_exit и отдельный module_exit, между ними опущен остальной текст файла.

Фрагмент `src/main.c`; многоточие обозначает пропуск.

```c
vb_params_set_ready(false);
vb_proc_exit();
vb_chardev_exit();
vb_worker_exit();
vb_can_exit();
// ... регистрация обработчика выгрузки:
module_exit(vb_exit);
```
