# Назначение интерфейсов

Действующий контракт, 22.09.2026. Управление работающей платой выполняется через `/dev/virtual_board`. Sysfs и procfs предназначены для наблюдения. Значения хранятся в `board.status`, а не в файлах интерфейсов. Персональные FIFO хранят снимки событий.

| Интерфейс | Назначение | Реализация / проверка |
| --- | --- | --- |
| `/dev/virtual_board`, write | `temp`, `limits`, `start`, `stop` | 22.09 подтверждены temp/start/stop; limits через ioctl |
| `/dev/virtual_board`, read | События процесса, ожидание и частичное чтение | 22.09 подтверждены одинаковые события двум читателям; граничные сценарии открыты |
| `/dev/virtual_board`, ioctl | GET_STATUS, SET_LIMITS, SET_PERIOD | 22.09 подтверждены три обычные команды; ошибки и период при running не проверены |
| `/sys/module/virtual_board/parameters/` | Чтение текущих температуры, пределов и периода; имени CAN-интерфейса | 0444; 22.09 чтение температуры, high_decic и period_ms согласовано с ioctl |
| `/sys/class/virtual_board/virtual_board/` | Чтение state и temp_status без дублирования числовых параметров | 22.09 подтверждены начальные stopped/normal, затем running → overheat → stopped/overheat |
| `/proc/virtual_board` | Общая сводка состояния и потерь событий | Реализовано; 22.09 проверены сводка, clients 0 → 1 → 0 и удаление при выгрузке; ненулевые потери ещё не проверены |
| CAN / vcan0 | Периодические статусы и уведомления при running | Прежняя версия проверена; новый ioctl периода требует проверки |

```text
write / ioctl через /dev → общая очередь команд → board.status
                                                   │
                         ┌─────────────────────────┼──────────────────┐
                         ↓                         ↓                  ↓
                  текущие значения          снимки событий     CAN при running
                  ioctl / sysfs             FIFO → read          → candump
                  proc (снимок при открытии)
```

`ioctl` — операция того же устройства, не отдельный файловый интерфейс. `boardctl` открывает `/dev/virtual_board` и вызывает ioctl. GET_STATUS не извлекает события из FIFO.

## Почему один cat ждёт, а другой сразу отвечает

Это выбранный контракт нашего драйвера, а не обязательное различие между dev и sysfs. Данные платы уже существуют в `board.status` после инициализации; ожидание событий не означает отсутствие этих данных.

| Способ чтения | Источник | Поведение |
| --- | --- | --- |
| `sudo cat /dev/virtual_board` | FIFO событий процесса | При пустой очереди ждёт; после события печатает строку и продолжает читать |
| `sudo ./tools/boardctl status` | Снимок `board.status` через ioctl GET_STATUS | Сразу показывает текущие значения и завершается; FIFO не расходуется |
| `cat /sys/class/virtual_board/virtual_board/state` | Поле state через `state_show()` | Сразу показывает running/stopped и завершается |
| `cat /sys/class/virtual_board/virtual_board/temp_status` | Поле temp_status через `temp_status_show()` | Сразу показывает normal/undertemp/overheat и завершается |
| `cat /sys/module/virtual_board/parameters/temperature_decic` | Текущая температура через callback параметра | Сразу показывает число и завершается |

```text
Открытие /dev новым читателем → пустой FIFO → read ждёт
Команда start → событие started → FIFO → read → строка в cat
                                                   → следующий read ждёт

Чтение sysfs → *_show() → значение из board.status под mutex
                       → текст → cat завершается
```

При открытии начальный снимок в FIFO не добавляется. События, произошедшие до появления читателя, для него не сохраняются. Периодические CAN-кадры не наполняют FIFO событий. Чтобы увидеть текущее состояние без ожидания изменений, используют GET_STATUS или sysfs. Файлы интерфейсов не являются отдельными хранилищами температуры и статусов.

Примеры управления и наблюдения:

```bash
sudo sh -c 'echo "temp 850" > /dev/virtual_board'
sudo sh -c 'echo "start" > /dev/virtual_board'
sudo ./tools/boardctl limits 100 700
sudo ./tools/boardctl period 1000
sudo ./tools/boardctl status
cat /sys/module/virtual_board/parameters/temperature_decic
sudo cat /dev/virtual_board
```

`cat /dev/virtual_board` получает новые события после открытия, а не начальный снимок. Для проверки рассылки его нужно запустить до команд. Два разных процесса имеют независимые FIFO; потоки и повторные открытия процесса разделяют один FIFO. После последнего читающего закрытия очередь очищается. Чтение чужого унаследованного открытия отклоняется с EXDEV; ребёнок открывает устройство заново. Закрытие такого открытия корректно освобождает исходную ссылку.

Начальные значения разрешено задавать при загрузке: `sudo insmod ./virtual_board.ko temperature_decic=250 low_decic=100 high_decic=700 period_ms=1000`. Это настройка до запуска модуля. После загрузки записи через sysfs нет, а чтение отражает последующие изменения через /dev. can_iface выбирается только при загрузке.

Модуль и утилита собраны для текущей среды x86_64; compat_ioctl для 32-битных приложений не реализован. Пользователь выполняет проверки с загрузкой самостоятельно. Сценарий `sudo python3 tests/test_params.py` требует vcan0 UP и выгруженного модуля, проверяет write/ioctl/sysfs/CAN и выгружает модуль после проверки. Он не заменяет проверку двух FIFO-читателей.

`cat /proc/virtual_board` получает отдельный снимок при открытии и завершается после EOF. Он не подписывается на события и не увеличивает clients. Строки pid/opens/readers/lost_events описывают процессы, открывшие /dev. Закрытие последнего открытия клиента удаляет его строку, но не останавливает CAN. Для свежей сводки файл нужно открыть заново.
